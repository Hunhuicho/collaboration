Principle

Every document keeps and displays its own status. An approval process, however, applies to PR and IR only — PO and DN move forward automatically. GR has no status of its own; posting a GR is the event that advances the PO (Partially / Fully Delivered) and the DN (Delivered).

Open question ① — what sets a PR / PO to Cancelled DECISION NEEDED

The original guide leaves the trigger blank. Below is a proposal to settle it — flag any row you disagree with.

The original question

There is no definition of when cancellation happens or who does it. For example:

  • Manual cancel by the requester before approval, or before goods receipt?
  • Automatic cancel when an approver rejects (reject → cancel)?
  • PO cancel only when no GR exists yet — or also after partial delivery?
  • Who has the authority to cancel, and is a reason required?
PROPOSAL

Cancellation triggers, authority and downstream handling

Cancellation is split by stage into allowed / needs agreement / not allowed, and the not-allowed stages are handled by other means (close short, credit memo).

ScopeConditionProposed trigger · handlingAuthorityDownstream
PRbefore approval OP / SM / UA Not a cancellation — withdraw the submission and delete. CN is not used Requester—
PRapproved · no PO Approved, no linked PO Cancel with a mandatory reason → PR_STATUS = CN Requester or Purchasing—
PRapproved · PO exists PR_STATUS = PO PR cannot be cancelled on its own. The PO must be cancelled first; the PR then follows to CN PurchasingPO cancellation required
PRrejected PR_STATUS = RJ Rejection is not cancellation. RJ never converts to CN automatically (see open question ②) Approver—
POjust issued PO_STATUS = OP, no GR Purchasing cancels → PO_STATUS = CN and notifies the supplier PurchasingLinked PR → CN or back to Open
POsupplier confirmed PO_STATUS = CF, no GR Supplier agreement required. Cancellation request → supplier accepts → CN Purchasing + supplierCancel the DN first if one exists
POpartially received PO_STATUS = PD Full cancellation not allowed. Handle as close short — what was received stays valid PurchasingOnly the open quantity is closed
POinvoice received IR_STATUS = OP / MC / PS Cancellation not allowed. Use a return or a credit memo instead Purchasing + FinanceLinks to the AP document
Cancel (CN)

Voids an approved document for a business reason. History stays; nothing moves on

Reject (RJ)

Sent back by an approver. Rework, not cancellation

Close

Stop receiving the remainder. What already happened stays valid

Delete

Remove a pre-approval document. Not kept for audit

Applies to all rows: cancellation requires a reason code plus free text, and the cancellation record (who, when, why) is written to the document history. Nothing cancels automatically — every cancellation is an explicit action.
05

Open question ② — can a rejected PR be reused DECISION NEEDED

This decides PR numbering, the audit trail, and how the approval restarts.

The original question

When a PR is rejected, can the requester edit the same PR and resubmit it (RJ → Open), or must a brand-new PR be created?

OptionBehaviourUpsideWatch out for
A. Reuse recommended RJ → OP, edit and resubmit. Approval history accumulates as revisions No re-keying, one number to track, rejection reason and the fix live in one document Approval history has to be stored per revision, and resubmission needs a rule for recalculating the approval chain
B. Create new The rejected PR is closed for good; copy it into a new PR One document = one approval. Clean from an audit point of view Numbers keep growing and the reject-and-redo trail is split across documents. Needs a reference field back to the original
Proposal: take A (reuse) as the default, with limits — for example resubmission is allowed within N business days of the rejection and only when the edit does not push the value into a different approval band; anything else needs a new PR. The rejection reason is mandatory and is kept per revision in the PR history.

A row that is green across all five columns is complete — received and invoice posted. An empty cell means that step has not started. Amber flags steps needing follow-up (partial delivery, invoice on hold); red and grey flag rejected or cancelled requisitions.
